How to use and review the challenge frontend

This guide explains what each control shows, what the evaluation button does, and how to review a run.

1. Team / case dropdown

Select the team whose business case you want to evaluate. The list comes from the Data API and only shows teams allowed by the configured token.

Changing the team automatically reloads that team's public scenarios.

2. Public scenario dropdown

Select the development scenario to test. Each scenario changes visible business conditions such as demand, supplier risk, capacity, or other operating signals.

The Manager must solve the selected scenario; it should not assume every scenario needs the same plan.

3. Manager LLM dropdown

Select the foundation model used only for the Manager/orchestrator. The rest of the system stays the same: PyTorch models, RAG, Skills, tools, simulator, and evaluator.

  • ready: the required API key is configured.
  • API key missing: that provider cannot run until its key is configured.

4. Run public evaluation

Runs the full agentic pipeline for the selected team, scenario, and LLM:

Manager → Skills → RAG → PyTorch → Tools → Plan → Simulator → Evaluator

This is a development test. It is not the hidden final course evaluation.

5. What the score cards mean

  • Operational: business result. For feasible plans it combines 35% feasibility, 25% service, and 40% cost. A critical feasibility violation gates Operational to 0.
  • Feasibility: whether the submitted plan respects hard operating constraints.
  • Service: realized service compared with the case service-level target.
  • Cost: cost score relative to the public benchmark for the scenario.
  • RAG: whether the agent retrieved the expected organizational evidence.
  • Skills / Tools: whether the agent used Skills, expected operational tools, cost/validation discipline, and an efficient tool workflow.

6. Scenario result and violations

Scenario result shows realized cost, benchmark cost, and percentage cost gap.

Constraint violations shows hard or soft simulator findings. Critical violations make the plan infeasible.

7. Evaluation breakdown

Use this section to understand why a score was assigned. It shows the Operational formula, RAG source coverage, loaded Skills/tool coverage, cost/validation use, efficiency penalties, and missing expected tools.

8. Agent trace

Review each tool call in order, including its inputs and outputs. Use the trace to answer questions such as:

  • Did the agent load a relevant Skill?
  • Did it retrieve the right RAG evidence?
  • Did it use the PyTorch model?
  • Did it inspect inventory/open POs?
  • Did it calculate cost and validate the plan?

9. Structured monthly plan

This is the final Pydantic-validated plan produced by the Manager. Review production orders, purchase orders, actions, assumptions, and explanation.

A plan can be feasible but still economically poor, so compare it with the cost score and trace.

10. Recommended testing workflow

  1. Select the assigned team.
  2. Select one public scenario.
  3. Select a configured Manager LLM.
  4. Run the public evaluation.
  5. Check feasibility and service first.
  6. Review cost and cost gap.
  7. Review RAG and Skills/Tools diagnostics.
  8. Inspect the Agent trace to confirm the architecture was actually used.
  9. Inspect the final structured plan.
  10. Change one component at a time (PyTorch, RAG, Skills, or LLM) and rerun so the effect is measurable.
  11. Repeat across multiple scenarios; do not optimize only for one scenario.

11. Logs and deeper debugging

The frontend summarizes the run; the server logs explain what happened internally. Each request receives an X-Trace-Id. Use that trace ID to correlate Manager, tool, RAG, model, Data API, simulator, and evaluator events in the logs.

See LOGGING.md for observability details and EVALUATION.md for the exact scoring rules.
