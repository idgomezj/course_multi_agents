# Student editable area

The runtime application, tools, simulator, cost engine and evaluator are provided and locked.

Your job is **not to program the platform**. Your job is to understand the assigned company, analyze imperfect evidence, configure the system, train the two assigned models, improve RAG and Skills, and explain why your decisions work.

Read `student-package/STUDENT_SOLUTION_GUIDE.md` before changing anything.

## Required workflow for every team

1. Call `/v1/teams/{team_id}/start-context` first and read the complete company/case context.
2. Read `training/CASE_TRAINING.md` and the fixed `training/model_contract.json`.
3. Download your own raw historical JSON from `/v1/teams/{team_id}/training-source.json`.
4. Analyze missing/noisy/duplicated/conflicting observations and document assumptions.
5. Build `model_a_training.csv` and `model_b_training.csv` from the raw evidence.
6. Tune `training_config.yaml` and `feature_config.yaml`; train both models.
7. Review the company knowledge documents and tune RAG + document authority.
8. Improve Skills for the operating procedures your company needs.
9. Tune forecast/risk/planning/tool/LLM/business-assumption configuration as appropriate.
10. Run several public scenarios, inspect the trace and diagnose *why* the system failed or improved.
11. Keep only changes you can defend from business evidence or experiments.
12. Expect hidden scenarios to combine known conditions differently; do not hardcode public scenarios.

## Where the training data comes from

The canonical Data API is:

```text
https://course-agentic-api.idgomezj.com
```

First:

```bash
curl -H "X-Client-Type: <your actual client/name>" \
  https://course-agentic-api.idgomezj.com/v1/teams/team_X/start-context
```

Then retrieve protected training evidence using your assigned team token:

```text
GET https://course-agentic-api.idgomezj.com/v1/teams/{team_id}/training-source.json
X-Team-Token: <token assigned to this team>
```

The API returns raw evidence, not ready-made ML rows. Do not replace it with another team's data and do not edit the raw evidence to make training easier.

## Fixed model contract

`model_contract.json` fixes:

- runtime feature names/order;
- output shape;
- task type;
- artifact name.

`feature_config.yaml` does **not** change that contract. Disabling a feature masks it to zero consistently in both training and inference so you can test whether it helps.

## Configuration-driven training

Use the supplied trainer:

```bash
python student/train_pytorch.py --team team_X --model model_a
python student/train_pytorch.py --team team_X --model model_b
```

The trainer reads:

```text
training/training_config.yaml
training/feature_config.yaml
```

You can experiment with:

- small / medium / large / custom hidden layers;
- activation;
- dropout;
- epochs;
- learning rate;
- batch size;
- Adam vs AdamW;
- allowed loss functions;
- weight decay;
- chronological vs random validation where permitted;
- validation fraction;
- feature masking.

A model is not automatically good because its training loss is low. Compare validation behavior and the final operational result.

## RAG and document authority

The Data API can intentionally provide useful, irrelevant, draft and obsolete documents.

`rag/config.yaml` controls retrieval settings.

`rag/document_priorities.yaml` lets you express the authority/priority you inferred from the company evidence. This changes retrieval ranking; it never changes the source document.

Do not mark a document obsolete simply because it makes the scenario harder. Be able to explain the evidence for the authority you assign.

## Forecast and risk configuration

`config/forecast_policy.yaml` controls the runtime `forecast_consensus` tool. It can combine:

- Model A;
- confirmed orders;
- moving average;
- exponential smoothing;
- seasonal forecast.

When uncertainty is high, configured multipliers can rebalance the signal weights.

`config/risk_policy.yaml` controls:

- low/medium/high risk thresholds;
- safety-stock factor;
- forecast-disagreement review threshold.

These are decision settings, not changes to the evaluator.

## Planning objectives and hard constraints

`config/planning_objectives.yaml` expresses **student preferences** for trade-offs such as service, cost, ending inventory and plan stability.

The actual company's hard constraints come from the case. If the company has:

- a monthly operating budget;
- warehouse limit;
- overtime limit;
- expedite cap;
- service policy;
- supplier/MOQ/approval constraints;

the simulator enforces those constraints independently. You cannot relax them by changing your YAML.

## Tool policy

`config/tool_policy.yaml` tells the Manager how you want it to use existing tools.

The tool implementations are locked. At minimum, the final decision process should retain cost and validation discipline. The goal is neither to skip necessary tools nor to call every tool without purpose.

## Manager LLM settings

`config/manager_llm.yaml` exposes bounded settings such as provider preference, temperature, token budget, reasoning mode and RAG-context limit.

API keys remain environment configuration and must never be stored in this file.

## Business assumptions

Use `assumptions/business_assumptions.yaml` for explicit assumptions that you can defend from:

- start-context;
- raw history;
- RAG documents;
- scenario-visible evidence;
- experiments.

Do not present an unsupported assumption as a company fact.

## What you are NOT allowed to modify

You may not modify to improve your score:

- Manager/runtime implementation;
- backend/framework;
- frontend;
- tool implementations;
- schemas;
- simulator;
- cost engine;
- evaluator/scoring;
- evaluation strategy or weights;
- hidden scenarios/holdouts;
- benchmark solutions;
- Data API;
- model I/O contract.

## How to know what to change

Do not change everything at once.

A useful loop is:

```text
observe → form hypothesis → change one controlled area → retrain/rerun → compare → keep/revert → document
```

Examples of diagnoses:

- weak validation metrics → investigate data construction, feature selection or training settings;
- Model A conflicts with orders/statistical forecasts → investigate forecast policy and evidence;
- stockouts despite reasonable forecast → inspect risk policy, inventory, POs, capacity and Skills;
- RAG returns old/irrelevant policy → inspect query, chunking and document authority;
- plan is cheap but infeasible → inspect hard constraints and tool/Skill workflow;
- too many unnecessary tool calls → improve Skills/tool policy;
- good public result but fragile behavior across scenarios → reduce scenario-specific assumptions.

The goal is to make a system that generalizes, not to discover one magic YAML file.
